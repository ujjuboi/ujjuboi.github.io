## Title: Teaching CI to Think: Agentic Workflows on GitHub Actions

## Date: June 30, 2026

## Excerpt: How we turned a modular monolith migration plan, code review, linting, PR descriptions, documentation, and regression tests into autonomous AI-powered GitHub Actions workflows.

## Banner: ../../Images/Graphics/GithubActions.svg

## Category: Deloitte

## Paragraphs

- <p>Between December 2025 and June 2026, we served as Software Engineers on Deloitte's DI App Factory team. The most interesting work wasn't a feature on the product roadmap — it was turning our own software development lifecycle into software. We built a family of AI-powered <em>agentic workflows</em> on GitHub Actions that reviewed code, enforced standards, described changes, updated documentation, and generated regression tests — autonomously, but safely.</p>
- <p>Before agents came architecture. We designed our migration roadmap from modular monolith to microservices using domain-driven design: event-storming sessions mapped core domains (identity correlation, ingestion, analytics, workflow orchestration) into bounded contexts with explicit ownership boundaries. Each context got a contract — synchronous REST for query paths, asynchronous event-based communication for state changes. The deliverable was a sequenced roadmap letting teams extract services incrementally, starting with the context that had the fewest inbound dependencies.</p>
- <p>The agentic workflows tackled mechanical judgment — work that needs intelligence but not creativity. Workflows live in Markdown files: prose instructions plus YAML front matter declaring which LLM engine to run (Copilot, Claude, or Codex), which toolsets are allowed, and which outputs the agent may produce. The <code>gh aw</code> CLI compiles these inside GitHub Actions, so an 'AI step' is just another pipeline step — versioned in git, reviewable in a PR, and observable like any other job.</p>
- <p>Guardrails mattered more than model choice. Every workflow ran under least privilege: read-only token by default, explicit tool allowlist, no direct write access. All agent output flowed through <em>safe outputs</em> — structured channels turning suggestions into review comments, labels, or issues — never direct commits. PR payloads contained untrusted content; workflows treated them as input data, never instructions. Pinning action versions, capping duration, and keeping every decision auditable in run logs were non-negotiable.</p>
- <p>The first workflow shipped was the <strong>Grumpy Code Reviewer</strong>. Built on <code>tools.github</code>, it pulled PR diffs, walked changed files with repository context, and left line-anchored comments — blunt about error handling, unforgiving about missing test coverage, opinionated about naming. The persona reduced nitpicking ambiguity and made feedback consistent across reviewers. It ran on every <code>pull_request</code> event, so authors got feedback in minutes. Human review didn't disappear; it got faster because reviewers stopped spending attention on mechanical issues the agent flagged.</p>
- <p>Intelligent lint-checking combined classic tooling with contextual judgment. A bash toolset executed real linters, while repository context tools fed the agent our actual conventions — directory structure, module boundaries, patterns from neighboring code. The agent flagged things static configs couldn't: duplicated utilities, API routes bypassing middleware, components importing across bounded-context lines. Severities separated cleanly: standards violations failed checks, stylistic suggestions landed as non-blocking annotations. One especially valuable rule prevented drive-by reformats that inflated diffs and buried real logic in review noise.</p>
- <p>PR descriptions went from paperwall to context-commits. A workflow combined <code>issues</code> and <code>pull_requests</code> toolsets: fetched the linked issue, diffed the branch, asked a summarization agent to reconcile them. Output followed a fixed contract — concise summary, bullet changes grouped by concern, testing notes, risk callouts. Safe outputs wrote it into the PR description field. Every PR now documented its scope, linked context, and blast radius — making review and later archaeology dramatically easier. Release notes nearly wrote themselves.</p>
- <p>Documentation drift was the next target. We built <em>Continuous AI</em> workflows on a schedule — cron-triggered GitHub Actions using <code>web-fetch</code> and <code>web-search</code> to watch upstream sources: API definitions, changelogs, internal wiki pages. When relevant content changed, the agent drafted Confluence updates producing diff-style summaries pushed through safe-output integrations. Documentation reviews became small, frequent, and current instead of pre-release scrambles.</p>
- <p>Regression testing was the most ambitious. Using Playwright, an agent received three inputs — issue context, PR metadata, and browser automation access to staging — and generated end-to-end test specs covering affected flows. Generated tests were reviewed like code before entering the suite; existing regression packs executed as release-validation gates. LLM browser automation fails loudly: a mismatched selector or unexpected flow produces evidence, not silent passes. Generated specs required human approval — test authoring automated, test judgment never abdicated.</p>
- <p>Engine choice (Copilot, Claude, Codex) was thresholded and configured per task, not hardwired. Long-context models handled sprawling diffs holding whole changes plus linked issues in view; faster models excelled at narrow jobs like description summarization. Prompt structure mattered more than model brand. Every prompt followed the same skeleton — role, scope, output contract, constraints — and we iterated against a small corpus of past PRs as an evaluation set. Treating prompts as tested artifacts, not incantations, was probably the single highest-leverage habit we built.</p>
- <p>Agents failed instructively. Early reviewers invented file paths (hallucination), so we required findings to cite concrete files and line ranges pulled through tool calls, not model memory. Over-eager agents produced comment spam; we tuned severity thresholds, deduplicated across runs, capped comments per PR. Silent partial failures eroded trust fast — steps validated their own outputs and failed loudly when something looked wrong. Each incident became a permanent evaluation case, replayed against future prompt changes.</p>
- <p>Six months in, the takeaway: agents amplify process quality in both directions. With contracts, scoped permissions, and safe outputs, they compress hours of mechanical judgment into minutes. Without them, they compress chaos too. Start with one narrow workflow, measure it like production software, keep guardrails boring — and let the interesting part be what your team builds once the busywork runs itself.</p>
